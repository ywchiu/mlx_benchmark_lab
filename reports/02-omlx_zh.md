# omlx 詳細報告

[English Version](02-omlx.md)

## 怎麼跑這個測試

```bash
# omlx 找模型只看 ~/.omlx/models/<model_id>/，不會讀你的 HuggingFace cache。
# 用 symlink 連過去就好：
ln -snf \
  ~/.cache/huggingface/hub/models--mlx-community--Qwen3.6-35B-A3B-4bit/snapshots/<HASH>/ \
  ~/.omlx/models/Qwen3.6-35B-A3B-4bit

omlx serve --port 8765 --log-level warning --no-cache
```

關於這個 API 有幾件事要先說清楚。omlx 用目錄基本名稱當 model ID，不是 HuggingFace repo 路徑——所以 client 發請求時，`model` 欄位要填 `Qwen3.6-35B-A3B-4bit`，不是 `mlx-community/Qwen3.6-35B-A3B-4bit`。`--no-cache` 同時會停掉記憶體裡的 prefix cache 和 SSD cache；不加這個參數的話，重複測試會撞到 cache，prefill 數字就不會反映冷啟動效能。

## 數據說明

omlx 是這次 benchmark 的長脈絡冠軍，數字本身就把這個論點說得清清楚楚。從 4K 開始它在每一格都是 decode tps 最高，到 32K 還能維持每秒 82 token——比 rapid-mlx 快 14%、比 dflash-mlx 快將近 6 倍。decode 衰退曲線也是這次最平緩的：從 64 到 32K 只掉 34%，rapid-mlx 是 42%，dflash-mlx 是慘烈的 92%。

更厲害的或許是它的穩定性。看一下 TTFT 的標準差：512 token 是 3 ms、2K 是 4 ms、4K 是 25 ms。其他框架在這個區間的變異都是 100 ms 起跳。如果你在做有嚴格延遲要求的服務——比如要對下游消費者承諾 p99 延遲——omlx 會讓這種承諾容易兌現。多數脈絡長度下 decode tps 標準差都在 1 tps 以內，這真的很罕見。

omlx 的 prefill 數字也是這次測試最高，4K 脈絡時來到每秒 3,989 token。這明顯領先 mlx-vlm（3,672）與 rapid-mlx（3,070）在同樣 prompt size 的表現。對於每次請求都要塞 4K–8K 檢索內容的 RAG 應用，這直接轉化成更快的端到端回應時間。

少數的弱點都很輕微。64 token 的 decode tps 是 123.7，比 rapid-mlx 的 124.9 略低——但這個差距在誤差範圍內。16K 和 32K 的 TTFT 變異會放大到 100–400 ms，比短脈絡時抖動更多，但仍然比其他框架穩。

## 什麼時候該用 omlx

任何 production 部署的預設選擇就是它。長脈絡 RAG、文件摘要、大檔案的程式碼分析、多租戶 inference server——omlx 會在最少調整的前提下給你最可預期的效能。

多模型管理是其他框架沒有的真實 bonus。omlx 支援同時載入多個模型、用 LRU 排出記憶體；你可以在同一個 server 上不重啟切換 Qwen、Llama、Mistral。對於要測許多模型、或要同時跑 chat 模型和程式碼模型的開發環境，這個功能很實用。

如果你只有短 prompt、又要榨乾每一個 decode token——dflash-mlx 在那邊更快。也別在你想對 cache 記憶體和 KV 量化做精細控制時選 omlx，因為 omlx 暴露的旋鈕比 rapid-mlx 少。

## 注意事項

設定的入門門檻是真實的痛點。omlx 要求模型放在 `~/.omlx/models/<id>/`，不會直接讀你的 HuggingFace cache。修法是一行 symlink，但要遇到「Available models: (none)」的錯誤訊息之後才會發現這件事。預設的 `~/.omlx/settings.json` 也把 `max_context_window` 卡在 32,768——如果你想測 64K 或 128K 脈絡，先把這個調高。

`/admin/api/...` 的管理 API 需要 cookie 認證，而 cookie 只能透過 `/admin` 的網頁 UI 登入後才能拿到。沒有什麼好辦法可以用腳本「載入這個模型」，只能另起一個 server 並在啟動時就指定模型——這次 benchmark 用的就是這個做法。如果你要做自動化測試，這是個摩擦點。

預設的 `--cache`（也就是不加 `--no-cache` 的情況）會同時開 SSD cache（寫到 `~/.omlx/cache/`）和記憶體裡的 prefix cache。做 benchmark 時兩個都關。production 用途則應該開著，那時候 cache 是你的朋友。
