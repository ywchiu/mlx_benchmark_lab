# rapid-mlx 詳細報告

[English Version](01-rapid-mlx.md)

## 怎麼跑這個測試

```bash
rapid-mlx serve mlx-community/Qwen3.6-35B-A3B-4bit \
  --port 8765 --disable-prefix-cache
```

`--disable-prefix-cache` 這個 flag 不是可有可無，是必加。rapid-mlx 預設會把 prompt 的前綴快取起來以加速重複請求，可是在 benchmark 這種「每次 run 都用同一個 prompt」的情境下，那份快取會讓第二到第五次 run 直接跳過 prefill 計算，最後你會看到 prefill 速度衝到每秒幾十萬 token——對 35B 模型而言這是物理上不可能的數字。我們在第一輪測試時就被這個坑了一次。把快取關掉之後，每一次量到的才是真實的冷啟動 prefill 表現。

## 數據說明

rapid-mlx 的強項是短脈絡 decode。在 64 到 512 token 的區間它穩穩排在領先群裡，每秒 119–125 token，而且更重要的是這些數字幾次 run 之間幾乎不動——32K 的標準差只有 0.2 tps，是這次測試所有框架裡最低的。如果你的服務需要對外承諾延遲，這種穩定性會幫你省下很多麻煩。

64–512 區間的 prefill 數字異常偏低（456 與 1,026 tps），跟 omlx 與 mlx-vlm 在 512 都能跑 1,800 tps 以上比起來明顯落後。我們推測這是 chunked prefill 在小 prompt 上不夠優化所致——rapid-mlx 是為「批量到達、可批次化」的 production 流量設計的，不是為「單一小 prompt」這種 micro-benchmark 場景。一旦 prompt 超過 2K，prefill 就跳到 3,000 tps 以上，回到競爭水準。

它的弱點在小脈絡的 TTFT 抖動。64 token 的中位數是 169 ms，但五次 run 中最大值飆到 462 ms——意思是某些請求毫無理由地慢了將近三倍。標準差 136 ms 跟中位數本身相當，這對在意延遲一致性的應用是個警訊。到了 4K 脈絡，這個抖動降到中位數的約 10%，所以只有短 prompt 工作負載會明顯受影響。

decode 隨脈絡長度的衰退是穩定且可預期的。從 64 到 32K，中位數從 124.9 跌到 72.3 tps，掉了 42%。這比 omlx 的 -34% 差，但比 mlx-vlm 好。絕對速度上，rapid-mlx 在 16K 就把長脈絡王座讓給了 omlx——那時 omlx 已經快它 22%。

## 什麼時候該用 rapid-mlx

當你需要短到中等脈絡的 decode、又能容忍一定的 TTFT 抖動時，它是對的選擇。rapid-mlx 在這四個框架裡功能組合最豐富（paged KV cache、multi-token prediction、prefix cache、KV cache 量化都有），是個適合測試新優化技巧的實驗平台。如果你在做的是處理 1K–4K 脈絡的 coding agent、又想能夠調整 cache 記憶體與 prefix cache 大小等參數，rapid-mlx 給你的旋鈕最多。

它不適合超長脈絡工作負載（16K 之後 omlx 勝），也不適合 SLA 導向、TTFT 一致性比峰值速度重要的應用。

## 注意事項

`/no_think` 這個 Qwen3 慣例在 rapid-mlx 上不太管用。模型還是會吐 reasoning token（streaming 中的 `reasoning_content` 區段），更糟的是 `max_tokens=256` 並不會限制 thinking 階段——我們看過長達 2,155 token 的輸出（1,879 個 thinking + 276 個可見內容）。如果你需要嚴格控制輸出長度，得在 client 端過濾 `reasoning_content`，或透過 chat template 參數傳 `enable_thinking=false`。

健康檢查 endpoint 在 `GET /health`，模型載入完成後會回傳 `{"ready":true}`，這就是 benchmark 開跑前該輪詢的端點。不要用 `/v1/models`——那個在啟動時就立刻可用，但模型其實還沒載好。
