# mlx-vlm 詳細報告

[English Version](04-mlx-vlm.md)

## 怎麼跑這個測試

```bash
python3 -m mlx_vlm server \
  --model mlx-community/Qwen3.6-35B-A3B-4bit \
  --port 8765
```

mlx-vlm 是這組裡的視覺語言模型（VLM）框架，主要用途是把圖片、影片、聲音跟文字一起送給多模態模型。我們這次只測純文字輸入，一方面為了讓比較公平（其他三個框架都只支援文字），另一方面因為 Qwen3.6-35B-A3B-4bit 模型可以透過 mlx-vlm 的 stack 處理純文字請求。值得注意的是 mlx-vlm 同時支援 `--draft-model` 配 `--draft-kind dflash`，理論上可以結合 vlm 的強 prefill 跟 dflash 的 decode 加速——這個組合本次沒測，但是個明顯的後續實驗目標。

## 數據說明

mlx-vlm 在我們測試的每個脈絡長度都有最低的 decode 吞吐量，短脈絡下落後第二慢的框架 25–30%，32K 時也比 omlx 慢 18% 左右。這是純文字請求要走過視覺語言 stack 的代價——inference pipeline 裡有 tokenizer 和 processor 層，純文字輸入用不到，但仍然存在。

但它有兩個補強的長處。第一，變異程度極低。64 跟 512 token 五次 run 的標準差只有 0.2 tps——這是這次測試任何脈絡長度任何框架裡最低的。如果你優化的目標是可預測性而不是峰值速度，mlx-vlm 的一致性異常突出。第二，prefill 表現優異。mlx-vlm 在 8K 脈絡時拿到所有框架的最高 prefill 速率（每秒 3,818 token），到 32K 也跟 omlx 不相上下。所以雖然每個 token 的生成速度慢，但每個 token 的 prompt 吸收速度卻是最快的之一。

decode 衰退曲線也是本次最平緩的：從 64 到 32K 只損失 29% 的 baseline 速度，比 omlx 的 34% 還略好。這部分原因是 64 token 的 baseline 本來就低——能損失的就少——但 32K 的 67.7 tps 仍然把 dflash-mlx 甩在後面，跟 rapid-mlx 的 72.3 也相去不遠。

2,048 token 那一格的變異比鄰近格大（標準差 4.1 tps，最小 83 最大 93）——可能是那一個尺寸下偶爾跑出一兩次比較慢的 run。撇除離群值不算，mlx-vlm 整體還是緊密集中。

## 什麼時候該用 mlx-vlm

老實說的答案是：當你需要把視覺、聲音、影片送進模型時。其他三個框架都不支援這些輸入，所以對任何多模態用例，mlx-vlm 是這組裡唯一的選擇。本次測試用的 Qwen3.6-35B-A3B-4bit 模型本身就支援多模態——它的 preprocessor config 裡含有視覺元件——所以餵圖片給它只是 request payload 改一個 flag 的事。

純文字場景下，除非你特別重視低變異而不是峰值吞吐量，否則很難推薦 mlx-vlm 而不選 omlx。短脈絡 25–30% 的 decode tps 差距是真實的代價，rapid-mlx、omlx、dflash-mlx 都會在它們各自的甜蜜點打贏 mlx-vlm 的絕對速度。

值得探索的中間地帶是 mlx-vlm 對 `--draft-kind dflash` 的支援。如果你的脈絡是中等（8K 以下）、輸出可預測，或許可以結合 mlx-vlm 的強 prefill 跟 dflash 的 decode 加速。這會驗證 speculative decoding 的好處跟 mlx-vlm 的 prefill 效率是相加的，還是會互相抵銷。我們沒測這個組合——是這輪最有意思的後續實驗。

## 注意事項

預設 port 是 8080，會跟很多其他工具撞到。我們明確把它設成 8765 來跑 benchmark。沒有 `/health` endpoint，用 `GET /v1/models` 檢查就緒狀態。

`--prefill-step-size` 參數（預設 2048）控制每個 prefill 批次有多大。對非常長的 prompt 你或許想調這個；較小的值用比較少的記憶體，但花比較多 wall-clock 時間。我們測試時用的是預設值。

mlx-vlm 比 rapid-mlx 跟 omlx 都更嚴格地遵守 `/no_think` Qwen3 慣例——輸出剛好停在 256 token（max_tokens 限制），完全沒吐 reasoning_content。所以如果你需要對輸出長度跟內容做乾淨的控制，mlx-vlm 是這組裡最聽話的框架。

CLI 也有 `python3 -m mlx_vlm generate`（單次推論）和 `python3 -m mlx_vlm convert`（模型準備）。我們 benchmark 用的是 streaming server（`python3 -m mlx_vlm server`）。順帶一提，`mlx_vlm.generate` 的棄用警告建議改用新的 `mlx_vlm generate` 形式。
